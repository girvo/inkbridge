InkFlow.app — Phase 4 plan

Working directory: /Users/josh/code/supernote-examination/inkflow-app (its own git repo, empty as of writing).

1. Goal

Wrap ../phase3/inkflow.swift in a proper macOS menu bar app so daily use doesn't involve running a CLI binary. The script already does everything functionally; this phase is about packaging — installable .app, stable bundle identifier (so TCC permissions stick across rebuilds), a status item that shows whether the device is connected, and a small menu for toggles.

Out of scope: changing the HID or CGEvent logic. Those are settled. Re-architecting MVM beyond what's needed to fit it into an AppKit lifecycle. Networking, sync, login, Firebase — explicitly not InkFlow's job.

3. Tech-stack decisions

3.1 Xcode project, not SwiftPM (recommended)

Menu bar apps need an .app bundle with a specific Info.plist (LSUIElement = YES to hide from the Dock), proper code signing, and a stable CFBundleIdentifier for TCC. SwiftPM can produce this with a manual wrapper script, but Xcode does it natively with one click. The .xcodeproj diff cost is real but acceptable for a single-target app.

Alternative: SwiftPM + a scripts/bundle.sh that builds the binary and assembles an .app structure around it. Viable if we want zero-Xcode tooling, but defer until / unless we hit friction with the Xcode flow.

3.2 Programmatic AppKit, no Storyboard, no SwiftUI

The whole UI surface is a status item, a menu, and one permissions window. SwiftUI buys us nothing for that, and Storyboards add file-format weight. Plain Swift + NSStatusItem, NSMenu, NSWindow.

3.3 macOS 13+ target

Reasons:

  • SMAppService.mainApp (the modern "launch at login" API) needs macOS 13.
  • IOHIDCheckAccess for Input Monitoring permission status was stabilized around macOS 12; macOS 13 is the safe baseline.
  • User is on macOS 26 (Darwin 25.4). No reason to support anything older.

5. Architecture

Two layers inside the single app target — keep AppKit out of the core so the core stays unit-testable and reusable (e.g. for a future CLI rebuild):

LayerFilesKnows aboutDoesn't know about
Core MacOSVirtualMouse, SupernoteHID, fields, key codes CoreGraphics, IOKit, Foundation AppKit, NSStatusItem, UserDefaults, the menu
App AppDelegate, InkFlowController, StatusItemController, PermissionsWindow, Preferences AppKit, Core, UserDefaults, SMAppService HID byte layout, CGEvent field IDs

The lifecycle owner is InkFlowController: holds the MacOSVirtualMouse instance and the SupernoteHID reader, exposes start() / stop() and an observable connection state. StatusItemController observes that state and updates the menu bar icon + first menu item.

6. Sub-phases

4.1 — Skeleton ✓ done 2026-05-14

  • Create Xcode project via XcodeGen (project.yml is the source of truth; InkFlow.xcodeproj is committed alongside). Bundle ID com.jgirvin.inkflow, deployment target macOS 13.0, Swift 5, ad-hoc signing baked into the spec (CODE_SIGN_IDENTITY = "-", CODE_SIGN_STYLE = Manual, no team).
  • Info.plist: LSUIElement set to YES — no Dock tile, app lives in the menu bar only. Also belt-and-braces: main.swift calls NSApp.setActivationPolicy(.accessory).
  • Programmatic AppKit bootstrap in InkFlow/App/main.swift (no Storyboard, no @NSApplicationMain, no @main — those proved unreliable for this lifecycle; see Notes).
  • Placeholder NSStatusItem with SF Symbol scribble.variable (template-mode so it adapts to light/dark menu bar) plus an NSLog fallback path if the symbol fails to load and a "Ink" text fallback for the button. Menu has a single "Quit InkFlow ⌘Q".
  • Built with xcodebuild -scheme InkFlow build; verified ad-hoc signed (codesign -dv reports Signature=adhoc, TeamIdentifier=not set). Launched from terminal, status item visible, no Dock icon, Quit functional. Initial commit.

4.2 — Embed the phase3 logic

  • Copy ../phase3/inkflow.swift into the project and split it into Core/MacOSVirtualMouse.swift, Core/SupernoteHID.swift, Core/CGEventFields.swift, Core/KeyCodes.swift. Drop the main at the bottom — replaced by AppKit's main loop.
  • Remove CLI-arg parsing; instead, expose properties (enableTabletFields, excalidrawMode, etc.) that InkFlowController sets from Preferences.
  • Create App/InkFlowController.swift: owns one MacOSVirtualMouse and one SupernoteHID; exposes start(), stop(), and a published connectionState: .disconnected / .connected(name:).
  • AppDelegate.applicationDidFinishLaunching calls controller.start(); applicationWillTerminate calls controller.stop() so the device is cleanly released.
  • Smoke test: launch app, plug device, enable InkFlow on Supernote — cursor follows exactly like the CLI did. Commit.

4.3 — Status reflection

  • SupernoteHID already has plug/unplug callbacks. Forward them as a closure into InkFlowController so it can update connection state.
  • StatusItemController swaps the status-item image and updates the first menu item text:
    • Connected: filled icon + "Connected: Supernote Nomad (SN…)"
    • Disconnected: outline icon + "Waiting for device…"
  • Optional: tint the icon (accent color) while a pen sample was received in the last ~200 ms. Visual heartbeat. Defer if it feels gimmicky.

4.4 — Permissions UX

This is the highest-friction part of the current CLI experience and the main reason we're bundling. Move from "cryptic CGEventPost silently no-ops" to "clear window with two checkmarks and buttons that open the right settings pane."

  • On launch (before start()): check
    • AXIsProcessTrusted() → Accessibility
    • IOHIDCheckAccess(kIOHIDRequestTypeListenEvent) → Input Monitoring
  • If either is denied, show PermissionsWindow instead of starting the controller. Window contents (one per missing perm): 
    [ ] Accessibility — required to inject pointer events
    [Open System Settings…]    [Why?]
[✓] Input Monitoring — required to read the Supernote
    Granted.
  • "Open System Settings…" buttons hit the right URL scheme:
    • x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility
    • x-apple.systempreferences:com.apple.preference.security?Privacy_ListenEvent
  • Poll the trust functions every 1 s while the window is open; auto-dismiss + start controller as soon as both go green.
  • Menu item "Permissions…" reopens this window for re-checking.
TCC subject stability: the whole point of bundling is that TCC keys off the app's CFBundleIdentifier + code signature, not its filesystem path. As long as we keep the bundle ID stable and sign consistently (even ad-hoc), TCC grants survive rebuilds. Don't change the bundle ID after first release — it counts as a different app and forces re-grant.

4.5 — Settings & menu toggles

  • Preferences: thin wrapper around UserDefaults.standard with typed getters/setters for:
    • enableTabletFields — Bool, default true
    • excalidrawMode — Bool, default false
    • launchAtLogin — Bool, default false
    • targetDisplayID — Optional<CGDirectDisplayID> (Phase 4.6)
  • Menu items with .state = .on/.off reflecting each prefs value; toggling flips the pref and pushes new value into the controller.
  • Live-apply: changing a toggle should take effect on the next HID sample (no restart).

4.6 — Polish

  • Launch at login via SMAppService.mainApp: register() / unregister() driven by the prefs toggle. Verify the registration sticks after a reboot.
  • Multi-display. Add a "Map to display" submenu listing NSScreen.screens; chosen display's frame drives the X/Y scaling in MVM instead of NSScreen.main. Persist the choice as the CGDirectDisplayID, fall back to main if the saved one disappears.
  • App icon & menu-bar icon. Custom .icns (Dock fallback if user invokes via Spotlight; not strictly necessary with LSUIElement) plus the status-item icon. SF Symbols for v1, custom monochrome PDF for v2.
  • About panel. Standard NSApp.orderFrontStandardAboutPanel with credits and a link to this repo.
  • Optional orientation override. If the device's coordinate axes ever feel rotated/mirrored (depends how the user holds it), add a 4-way rotation pref. Don't build unless the user reports needing it.

9. Open decisions

  • Bundle identifier. Resolved: com.jgirvin.inkflow. Locked — TCC grants pin to this + signature.
  • Code signing. Resolved: ad-hoc (CODE_SIGN_IDENTITY = "-", no team). User accepts the one-time Gatekeeper override per Mac. Upgrade path to Developer ID + notarization stays open and keeps TCC grants stable (bundle ID is the load-bearing identifier).
  • Distribution. Build locally only? GitHub Releases with a built .app zip? Defer until v1 works end-to-end.
  • Status-item visual. Resolved for v1: SF Symbol scribble.variable in template mode. Reconsider if a custom monochrome PDF becomes worth designing.
  • Settings window vs menu-only. The menu is enough for current toggles. If we add display picker, orientation, custom keystrokes — a dedicated preferences window starts pulling its weight. Add when it does.

12. Notes & surprises

  • Xcode was not installed at session start. Only Command Line Tools were present, so xcodebuild -project InkFlow.xcodeproj failed initially. Installing Xcode from the App Store, switching the active developer dir with sudo xcode-select -s /Applications/Xcode.app/Contents/Developer, and accepting the license unblocked the build. Confirmed working with Xcode 26.5 / build 17F42 on macOS 26 (Darwin 25.4).
  • @main on NSApplicationDelegate is not a reliable pattern for programmatic AppKit menu-bar apps. The first iteration used @main final class AppDelegate: NSObject, NSApplicationDelegate; the app process started but no status item appeared. Switched to an explicit main.swift that instantiates the delegate, assigns it to NSApplication.shared, sets .accessory activation policy (defensive — LSUIElement in Info.plist should already do this), and calls NSApp.run(). This matches PLAN §4.1's original direction and should be the long-term pattern; do not regress to @main or @NSApplicationMain without testing.
  • SF Symbol fallback worth keeping. A failed NSImage(systemSymbolName:) lookup silently produces a zero-width status item button under variable length. AppDelegate.applicationDidFinishLaunching logs an NSLog diagnostic and falls back to a "Ink" title if the symbol disappears in a future SDK. Keep this guard when iterating on the icon.
  • XcodeGen is the source of truth. project.yml is hand-edited; xcodegen generate rewrites InkFlow.xcodeproj. Per user preference, both are committed. If a setting needs changing, edit project.yml and regenerate — don't hand-edit project.pbxproj directly, as the next regeneration would clobber it.

10. What "done" looks like

  1. Double-click the bundled .app → status item appears in the menu bar, no Dock tile.
  2. First launch: permission window asks for the two perms; granting them auto-dismisses and starts the pipeline. No re-prompts on subsequent rebuilds.
  3. Plug Supernote in, enable InkFlow on the device → status item updates to "Connected", cursor follows the pen with pressure + tilt.
  4. Unplug → status item goes to "Waiting for device". Re-plug → reconnects without intervention.
  5. Excalidraw mode toggle works from the menu, takes effect on next pen-flip.
  6. Reboot → app auto-launches (if pref enabled), starts headlessly, ready when device is plugged in.

11. Things explicitly NOT in this phase

  • Multi-device routing. One Supernote per Mac.
  • Per-app tablet-mode overrides. The user toggles globally.
  • Keyboard shortcut customization. Excalidraw keys are hardcoded for now.
  • Crash reporting / analytics.
  • Auto-update.
